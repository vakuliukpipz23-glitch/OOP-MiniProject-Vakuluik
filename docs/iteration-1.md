## 1. Що Працює Наразі

### Вертикальний Зріз: Реєстрація Відвідувача → Позичення Книги → Повернення Книги

Наступний повний сценарій працює від початку до кінця:

1. **Реєстрація Відвідувача**
   - Створення нового відвідувача з ім'ям, email, телефоном
   - Автоматичне генерування ID відвідувача
   - Валідація всіх полів введення
   - Статус: ПРАЦЮЄ

2. **Управління Інвентарем Книг**
   - Реєстрація книг з ISBN, назвою, автором, категорією
   - Автоматичне створення декількох фізичних копій
   - Відстеження статусу доступна/позичена/зарезервована/пошкоджена
   - Статус: ПРАЦЮЄ (3 зразки книг попередньо завантажені)

3. **Позичення Книг**
   - Пошук доступних книг
   - Перевірка права відвідувача
   - Створення запису позичення з терміном 30 днів
   - Позначення копії як позиченої
   - Статус: ПРАЦЮЄ

4. **Повернення Книг та Штрафи за Прострочення**
   - Повернення позичених книг
   - Автоматичний розрахунок штрафів за прострочення (0.50 за день після 0-денного періоду пільги)
   - Позначення копії як доступної знову
   - Відображення штрафів, якщо застосовується
   - Статус: ПРАЦЮЄ

## 4. Ризики та Невизначеності

### Відомі Обмеження

1. **In-Memory Зберігання**
   - Дані втрачаються при завершенні додатку
   - Не придатне для виробничого використання
   - Рішення: Реалізувати SQL персистентність в Lab 35

2. **Відсутність Контролю Конкурентного Доступу**
   - Декілька користувачів можуть позичити ту саму копію
   - Відсутня блокування або підтримка транзакцій
   - Рішення: Додати в Lab 35 з SQL транзакціями

3. **Спрощена Генерація ID**
   - Використовує DateTime.Ticks для генерації ID
   - Не глобально унікальні в розподілених сценаріях
   - Рішення: GUID або ідентифікатори бази даних в Lab 35

4. **Обмежені Сценарії Помилок**
   - Відсутня обробка мережевих збоїв
   - Відсутня обробка збоїв диска/бази даних
   - Рішення: Додати патерни стійкості в Lab 36

5. **Відсутність Асинхронних Операцій**
   - Усі операції синхронні
   - Може блокувати при повільному I/O
   - Рішення: Планувати async/await для Lab 35 з SQL

### Архітектурні Рішення

1. **Чому Паттерн Репозиторій?**
   - Дозволяє змінювати механізми персистентності
   - Вмикає in-memory тестування без бази даних
   - Дотримується принципу SOLID DIP

2. **Чому Шарова Архітектура?**
   - Чітке розділення відповідальності
   - Тестованість на кожному шарі
   - Загальний паттерн, легкий для підтримки

3. **Чому Валідація в Конструкторі?**
   - Запобігає існуванню невалідних об'єктів
   - Принцип fail-fast
   - Усі інваріанти гарантовані від створення

4. **Чому OverduePolicy як Сутність Домену?**
   - Бізнес-правила інкапсульовані
   - Може бути розширено з декількома політиками
   - Легко тестувати розрахунки незалежно
