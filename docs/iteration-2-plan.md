# План Ітерації 2 (Lab 35)

## Базові рішення
- Гілка: `lab35-business-and-persistence`
- Основна мета: розширити Lab 34 на збереження стану у файл та реалізувати бізнес-правила другого рівня.
- Використані точки розширення: `IDataStore<T>`, `LibraryPersistenceService`, `IOverduePolicy`, репозиторії.

## Сценарії, що переходять у реалізацію
- **Реєстрація нового відвідувача** — зберігається у стані, доступна для повторного запуску програми.
- **Позичення книги** — застосовані бізнес-правила: доступність копій, борги, прострочення.
- **Повернення книги** — обчислення штрафів, оновлення статусу копії.

## Нові сценарії Lab 35
- **Пошук книг** за назвою, автором та категорією.
- **Аналітика**: активні позичення, прострочені позичення, топ-позичених книг.
- **Оновлення інфо**: змінити контакт відвідувача, змінити категорію книги.

## Що лишається без змін
- Доменні класи: `Book`, `Copy`, `Patron`, `BorrowRecord`, `OverduePolicy`.
- Контракти репозиторіїв та загальна архітектура шарів.
- Основні сервіси: `BookService`, `PatronService`, `BorrowService`.
- Консольний UI як точка входу.

## Точки розширення, що будуть використані
- `IDataStore<T>`: дозволяє легку заміну JSON на XML/SQL у майбутньому.
- `IOverduePolicy`/`OverduePolicy`: Strategy для зміни правил штрафів.
- `LibraryPersistenceService`: фасад для збереження та відновлення стану.
- `LibraryQueryService`: місце для додавання нових запитів без зміни інших сервісів.

## Ризики і невизначеності
- Конфлікти при відновленні стану: послідовність створення книг, копій і записів позичення.
- Обробка пошкодженого JSON-файлу та некоректних даних у `data/library.json`.
- Відсутність інтеграційних тестів для повного збереження/відновлення.
- Потенційне дублювання логіки вибору доступної копії та обробки статусів у сервісі і доменних класах.
- Можливі складнощі з перевіркою часу в бізнес-правилах `BorrowRecord.IsOverdue()`.
